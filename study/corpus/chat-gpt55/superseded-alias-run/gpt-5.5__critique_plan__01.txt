I don’t see the actual plan in your message, but for a 400-user weekend email migration, these are the areas teams most often miss or underestimate.

## Biggest things to verify

### 1. Pilot and rehearsal
- Run a pilot with a representative group before migration weekend: executives, heavy mailbox users, shared mailbox users, mobile users, Mac users, delegated-calendar users.
- Do at least one test migration end-to-end, including DNS cutover, client login, mobile setup, mail flow, calendar access, and rollback.
- Confirm actual migration throughput, not vendor estimates.

### 2. Detailed cutover runbook
You should have an hour-by-hour runbook covering:
- Who does what
- Exact commands or admin-console actions
- Start/stop times
- Go/no-go checkpoints
- Escalation contacts
- Vendor support contacts
- Decision owner for rollback
- Communication templates

Do not rely on “we’ll figure it out during the window.”

### 3. DNS and mail flow
Commonly missed:
- Lower MX/autodiscover/SPF/DKIM/DMARC-related DNS TTLs 48–72 hours before cutover.
- Plan for DNS propagation delays.
- Validate inbound and outbound mail flow.
- Update SPF records for the new mail platform.
- Configure DKIM signing.
- Confirm DMARC alignment.
- Confirm Autodiscover behavior.
- Update any SMTP relay records, scanners, applications, or mail-enabled devices.

### 4. Mailbox data scope
Make sure you know exactly what is being migrated:
- Email
- Calendar
- Contacts
- Tasks/notes
- Archive mailboxes
- Shared mailboxes
- Resource/room mailboxes
- Public folders
- Distribution lists/groups
- Mail-enabled security groups
- Aliases/proxy addresses
- Delegates and permissions
- Send As / Send on Behalf rights
- Calendar sharing permissions
- Retention tags or labels
- Litigation hold / legal hold data

Calendar permissions and shared mailbox access are especially easy to overlook.

### 5. Identity, authentication, and access
Confirm:
- User accounts already exist in the new system.
- Primary SMTP addresses match.
- UPN/login format is understood by users.
- Password sync, SSO, MFA, and conditional access are working.
- Licensing is assigned before cutover.
- Disabled/terminated users are handled properly.
- Admin and break-glass accounts are ready.

If MFA enrollment happens the same weekend as email migration, expect extra helpdesk volume.

### 6. Client and device readiness
Plan for:
- Outlook profile recreation or reconfiguration.
- Outlook for Windows/Mac differences.
- Mobile device re-enrollment.
- Native iOS/Android mail app behavior.
- Cached mode delays.
- Autodiscover failures.
- Legacy protocols: POP, IMAP, SMTP AUTH, ActiveSync.
- Users with multiple mailboxes.
- VIP and executive assistant scenarios.

Have clear instructions with screenshots ready before the weekend.

### 7. Applications and devices that send email
This is a common blind spot. Inventory and test:
- Scanners/copiers
- ERP/CRM systems
- Ticketing systems
- Monitoring tools
- Backup systems
- Websites/contact forms
- HR/payroll systems
- Line-of-business applications
- Printers using SMTP relay
- Security appliances
- Alerting systems

Decide whether they use direct send, SMTP relay, authenticated SMTP, API-based sending, or a third-party service.

### 8. Security, compliance, and governance
Validate:
- Retention policies
- Legal hold/litigation hold
- Journaling
- eDiscovery access
- DLP rules
- Transport/mail flow rules
- External forwarding policy
- Anti-spam/anti-phishing policies
- Safe links/attachments or equivalent
- Mailbox audit logging
- Admin audit logging
- Encryption requirements
- Data residency requirements

### 9. Backup and rollback
You need a real rollback plan, not just “we’ll change MX back.”

Define:
- What conditions trigger rollback?
- Who makes the decision?
- By what time must the rollback decision be made?
- Can source mailboxes still receive mail?
- Are source mailboxes still accessible?
- What happens to mail delivered to the new platform before rollback?
- Can users continue working from the old system?
- How do you avoid duplicate/lost messages?
- How will you preserve calendars and sent items created during the failed cutover?

Also confirm backups or recoverability before starting.

### 10. Communication plan
Prepare communications for:
- Pre-migration notice
- What users need to do before Friday
- What to expect over the weekend
- How to log in Monday
- Mobile setup instructions
- Known limitations
- Helpdesk contact info
- Executive/VIP-specific instructions
- Post-migration follow-up

Send reminders more than once. Users will miss the first email.

### 11. Support coverage
For Monday morning, plan for a spike.

Have:
- Extra helpdesk staffing
- Floor walkers or remote support bridge
- VIP support queue
- Known-issues document
- Fast escalation path to migration engineers
- Password/MFA support ready
- Device setup guides
- A triage process: access issue, missing data, mobile issue, Outlook issue, mail flow issue, permissions issue

### 12. Migration performance and throttling
Check:
- Mailbox sizes
- Total data volume
- Network bandwidth
- Source platform throttling
- Destination throttling
- API limits
- Large mailboxes
- Corrupt items
- Rate limits
- Retry behavior
- Delta sync timing

For 400 users, the number of users is less important than the total mailbox data size and the number of large/problematic mailboxes.

### 13. Data freeze and final delta sync
Consider:
- When do you stop changes in the old system?
- When is the last delta sync?
- Are users locked out of the old system during cutover?
- What happens to mail/calendar changes made during the weekend?
- How do you verify every mailbox completed successfully?

### 14. Post-migration validation
Have a checklist for Monday:
- Inbound mail works
- Outbound mail works
- Internal mail works
- External calendar invites work
- Mobile access works
- Delegates can access mailboxes/calendars
- Shared mailboxes work
- Distribution lists work
- Room booking works
- Applications can send email
- DNS records are correct
- DKIM/SPF/DMARC pass
- No major queues/backlogs
- No unusual authentication failures
- No excessive support trends

### 15. Legacy system decommissioning
Do not shut down the old system immediately unless you are very confident.

Plan:
- How long will it remain available?
- Will it be read-only?
- How will you handle straggler data?
- When will forwarding stop?
- When will old licenses be removed?
- What needs to be archived for compliance?
- When will final backups be taken?
- How will you document the final state?

---

## High-risk areas I would specifically challenge

If your plan does not include these, I would add them:

1. A completed pilot migration  
2. A tested rollback plan  
3. DNS TTL reduction before the weekend  
4. Mail flow validation including SPF/DKIM/DMARC  
5. Inventory of all SMTP-sending applications/devices  
6. Shared mailbox and delegate permission migration  
7. Room/resource mailbox testing  
8. Mobile device instructions  
9. MFA/SSO validation  
10. Monday morning support surge plan  
11. Final delta sync and verification process  
12. Executive/VIP white-glove support  

## My short recommendation

For 400 users, a weekend cutover can work, but only if you have already piloted, measured migration speed, and documented rollback. If this is the first real attempt, I would strongly consider a staged migration or at least migrate the heaviest/riskier mailboxes before cutover and use the weekend only for delta sync, DNS, client transition, and support.
