Use **PostgreSQL** for a booking system with ~50,000 records.

50,000 records is small for both Postgres and MongoDB, so the decision should be based on the data model and correctness requirements — not size.

For a booking system, Postgres is usually the better default because it gives you:

- **Strong transactions** to prevent double-booking
- **Constraints** like unique indexes, foreign keys, and check constraints
- **Reliable relational modeling** for users, bookings, rooms/items, payments, availability, etc.
- **Good querying** for reports, schedules, date ranges, filtering, and joins
- **Mature concurrency handling**

Example tables might be:

- `users`
- `resources` / `rooms` / `services`
- `bookings`
- `payments`
- `availability_rules`

You can enforce rules like:

```sql
UNIQUE(resource_id, start_time, end_time)
```

or use more advanced Postgres features like exclusion constraints to prevent overlapping bookings.

Use **MongoDB** only if your booking data is highly document-oriented and flexible, for example:

- Each booking has very different fields
- You rarely need joins
- You mostly read/write whole booking documents
- Strict relational integrity is not very important

But for most booking systems, especially where avoiding duplicate or overlapping reservations matters, **Postgres is the safer and more natural choice**.

**Recommendation: choose PostgreSQL.**
